# V0.7 — chat-controlled teams

## Milestone and acceptance decision

Ship a simple Codex app workflow in which the user selects the orchestrator in
Codex and changes the subagent model, roles, and concurrency through chat.
Acceptance requires working implementation, migration coverage, verified plugin
packaging, updated GitHub documentation and images, and a published commit and
release. A settings file or a green legacy suite alone is insufficient.

## User experience

- “Show my subagent setup.” is read-only.
- “Use GPT-6 Luna for this chat.” changes subsequent launches in this chat.
- “Use GPT-6.1 Sol for the critic.” is a supported explicit role override.
- “Use scout, worker, and critic, at most two at once.” changes team structure.
- “Save this for this project” persists project settings.
- “Make this my default” persists personal settings.
- “Reset my team” restores defaults in the explicitly selected scope.

An unqualified change applies to this chat. Do not interpret “switch” alone as
permission to change all future chats. Confirm the effective scope and values
in one sentence. Changes affect future launches, not running children. Report
runtime caps rather than claiming a policy preference raises them.

## Design decisions after adversarial review

1. The root model, reasoning, speed, provider, and permissions remain user-owned.
   Replace Sol-specific requirements with orchestrator responsibilities.
2. Keep roles as bounded assignment instructions. Prefer native generic agents
   with an explicit model and reasoning at launch, plus a self-contained role
   prompt. This supports immediate role edits without depending on hot-reloading
   named custom agents. Use fresh child context when the runtime requires it for
   model overrides. Do not use legacy model-pinned roles for flexible launches.
3. Default to GPT-6 Luna for new setups; preserve an existing explicit choice.
   Accept exact available model IDs or `inherit`, not ambiguous generation names.
   Resolve an ambiguous “6.1” conversationally using available models; never
   fabricate a Luna variant or silently substitute an unavailable model.
4. Store model, enabled role definitions, optional explicit role overrides, and
   concurrency in one small settings document. Defaults work without a file.
   Reuse the existing setup skill as the conversational entry point. No model
   pack registry, automatic premium escalation, daemon, or extra UI.
5. Resolve chat overrides over project settings over personal settings over kit
   defaults. Validate model/effort against runtime capabilities when exposed;
   distinguish configured from observed runtime values. If availability cannot
   be established, report it honestly and do not claim a successful launch.
6. For `inherit`, omit both model and effort unless the user explicitly selects
   a supported effort. Model-specific default reasoning must not accidentally
   inherit an unsupported root effort. Pin neither in generic role definitions.
7. Retain scope, ownership, acceptance checks, no nested delegation, and evidence
   requirements. Read-only role instructions are behavioral, not a separate
   sandbox. Service tier, provider, permissions, and MCP inherit from the root.
8. Keep historical policies, control bundles, and receipts immutable. Current
   diagnostics and receipts must understand flexible root/child models without
   comparing their metrics to old fixed-model benchmarks or inventing costs.
9. Migrate recognized legacy managed instructions and roles with backups and
   conflict detection. Preserve user edits and unrelated Codex configuration.
   Do not infer a pre-install root preference if old state never captured it.
   Any initial plugin reload requirement must be reported separately from later
   chat-only team changes.

## Work sequence

1. Inspect installer, setup/orchestration skills, hooks, receipts, CI, and release
   state; record compatibility constraints and current test baseline.
2. Implement the small settings resolver and deterministic read/update commands,
   scoped persistence, validation, and safe legacy transition.
3. Connect setup and orchestration skills to those settings and explicit native
   launches. Update guard/receipt/status behavior so old hard-coded policies do
   not reject valid current-model work or misreport it as verified.
4. Exercise realistic chat requests with model changes, role changes, inheritance,
   save/reset, conflicting settings, and unavailable capabilities. Verify actual
   spawn arguments where runtime tools permit; document unverified surfaces.
5. Refresh README, install/update docs, plugin metadata, and GitHub image assets.
   Render and inspect visuals, including small-screen legibility.
6. Run relevant new tests plus the complete suite, plugin mirror checks, skill
   validation, and clean-install/update simulations on isolated roots. Review
   failures for real compatibility bugs rather than weakening acceptance.
7. Commit, push, publish through the repository's actual GitHub workflow, verify
   CI and release contents, and verify README/images resolve on GitHub. Deploy
   means publish the installable plugin release; this is not a hosted service.

## Required checks

- Different supported root models do not cause policy/receipt rejection.
- A model change takes effect in subsequent launch arguments in the same chat.
- A pinned legacy custom role cannot silently override the chosen model.
- Inherit omits model/effort correctly; unsupported reasoning is rejected.
- Role selection and requested concurrency are enforced within runtime limits.
- Chat-only changes do not write persistent configuration.
- Project and personal saves have predictable precedence and rollback backups.
- Invalid settings, unsafe paths, malformed state, and edited legacy files fail
  without partial or unrelated mutations.
- Existing running agents are not silently reconfigured or cancelled.
- Historical receipts still read; new records distinguish requested and observed
  execution and leave unavailable usage/cost unknown.
- Expired historical rate cards do not make fixture tests depend on today's date.
- The plugin bundle matches canonical files; README/image claims match behavior.
- GitHub CI, published commit/tag, release assets, and install instructions agree.
